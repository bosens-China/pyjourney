手写 `__enter__` 和 `__exit__` 适合状态比较多的管理器。`contextlib` 覆盖几种反复出现的 `with` 写法。

## @contextmanager

`@contextmanager` 装饰一个生成器函数，这样就不必再写一个带两个特殊方法的类。生成器应当恰好产生一个值：`yield` 之前的代码充当 `__enter__`，产出的值在有 `as` 时绑定到目标；`yield` 之后的代码充当 `__exit__`。

执行到 `yield` 时，`with` 的代码块开始运行，块结束后生成器继续。块里未处理的异常会在 `yield` 那一点重新抛出，所以清理放在 `finally` 里。如果捕获异常只是为了记录或做一件事，生成器必须把异常重新抛出。没有重新抛出时，这个上下文管理器会告诉 `with`：异常已经处理，执行从 `with` 后面继续。

```python
from contextlib import contextmanager

@contextmanager
def override(store, key, value):
    missing = object()
    old = store.get(key, missing)
    store[key] = value
    try:
        yield  # [!code highlight]
    finally:  # [!code highlight]
        if old is missing:
            store.pop(key, None)
        else:
            store[key] = old
```

`finally` 在正常离开和异常离开时都会把这个键恢复。异常仍会继续传播，因为 `finally` 没有把它吞掉。

## suppress

`suppress(KeyError)` 用来标明：代码块里的 `KeyError` 是有意忽略的。该异常出现时，`with` 结束并继续后面的语句，其他异常仍然传播。它比写一个只有 `pass` 的 `except` 更直接。

```python
from contextlib import suppress

counts = {"known": 1}
with suppress(KeyError):
    del counts["missing"]
print(counts["known"])
```

## ExitStack

个数要到运行时才知道的管理器，用 `ExitStack.enter_context` 逐个进入。已经进入的管理器会在栈退出时执行自己的 `__exit__`；后面某一个进入失败时，前面进入成功的那些仍会退出。

```python
from contextlib import ExitStack

store = {"debug": False, "trace": False}
with ExitStack() as stack:
    stack.enter_context(override(store, "debug", True))
    stack.enter_context(override(store, "trace", True))
    print(store["debug"], store["trace"])
print(store["debug"], store["trace"])
```

代码块里两个键都是 `True`。栈退出后，两个 `override` 都把键写回 `False`。

| 阶段 | 管理器的执行顺序 |
| --- | --- |
| 进入 | `debug` → `trace` |
| 退出 | `trace` → `debug` |
